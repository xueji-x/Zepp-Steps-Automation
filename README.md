# Zepp 白天渐进更新 · GitHub Actions 版

每日计划目标 **8001–14999** 步。北京时间 **08:00–21:00** 活动，每 **30 分钟**一个时段，共 26 段，普通提交最多增加 **1000** 步。每日目标和时段权重随日期、账号变化；早晨、午间、傍晚权重较高。

代码不含真实账号密码，运行在 GitHub 托管机器上，不连接个人服务器。

## 为什么改为持续会话

2026-10-27 截至北京时间 19:26，GitHub 只产生 12:49、18:05 两次定时运行；两次接口都成功，但旧版每次最多增加 180 步，所以累计仅 360 步。这不是 Zepp 限流。当天经明确授权，已一次性补到 13159 步并保存进度。

当前版本使用 `7,37 0-12 * * *`（UTC，北京时间 08:07–20:37）作为半小时启动机会。一旦启动，会话会持续检查半小时时段，最长 **5 小时 30 分钟**；不再依赖每个半小时都必须触发一个新的 GitHub 任务。会话到期后保存进度，已排队的任务可接续。任务串行执行，新触发不取消正在运行的会话。

每天只有 26 个更新时段。同一时段重入不会重复增加；夜间退出；当天目标完成后立即退出。正常日志中的 `Waiting ... seconds` 表示等待下个时段，并非卡住。GitHub 界面会长时间显示运行中，这是预期行为。

运行步骤留有 350 分钟超时空间，低于托管任务六小时限制。会话正常结束或失败后，尝试保存最后成功上传的进度；强制取消、机器故障可能来不及保存。

## 配置与管理

仓库 Secrets 为 `ACCOUNT`、`PASSWORD`，使用 **Zepp Life** 凭据，不是 GitHub / SSH 密码。只向认证步骤提供，不写入代码、缓存、原始响应日志。

进入 **Actions → Zepp daytime increments**：

- 启动：启用工作流，或 `Run workflow → watch` 立即启动会话。首次触发仍由 GitHub 调度决定。
- 暂停：先 `… → Disable workflow` 阻止新任务，再进入正在运行的会话，点击 `Cancel workflow`。只 Disable 不会停止已开始的会话。
- 恢复：`Enable workflow`，然后 `Run workflow → watch`；也可等待下次定时触发。
- 查看状态：打开当前或最近一次运行的 `Run selected mode`，看提交结果和等待日志。会话结束后查看 `Save successful progress`。
- 修改运行文件提交到 main 时也会启动会话，以便检查部署。README 等文档变更不会启动。

`Run workflow` 的模式：

- `watch`（默认）：持续运行半小时时段，最长 330 分钟。
- `run`：只检查、提交当前时段的一次增量。
- `preview`：只展示当日计划，不登录、不提交。
- `check-login`：验证 Zepp 登录和 app token，不提交步数。
- `catch-up`：仅明确授权的特殊情况，填写北京时间当天 `catch_up_date`（YYYY-MM-DD），一次性补到完整目标。日期不符拒绝；普通自动任务不会进入此模式。

完全停用：Disable 工作流，Cancel 活跃会话，再删除两个 Secrets。删除仓库或代码不会撤回已上传的步数。

## 进度与限制

成功上传后，先更新本地进度；每段会话结束时写入 Actions Cache。缓存只含日期、账号散列、累计步数、时段号，不含密码或令牌。公开仓库缓存不应视为私密存储。

这个方案提高的是“某次启动后持续执行”的能力，**不能保证 GitHub 首次触发时间，也不能保证平台故障时全天达标**。很晚才启动、严重停机或凭据错误时，仍优先遵守每次 1000 步上限，不自动一次补满。公开仓库长时间无活动可能暂停定时任务。

每日上限仅约束本脚本；手机、手环或其他程序仍可能增加步数，不要并行运行其他步数修改程序。接口成功表示 Zepp 接受请求，微信最终同步需在 App 中确认，且账号需已绑定微信运动。

这是模拟累计值，不是真实步行传感器记录，分钟传感器数据未重建，不保证平台判为真实活动。勿用于奖励、捐步或其他要求真实活动的场景。
